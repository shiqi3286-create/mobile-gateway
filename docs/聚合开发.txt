个人移动聚合网关项目开发进度
==============================

一、项目概述
------------
项目名称：Android 个人移动聚合网关
当前仓库：https://github.com/shiqi3286-create/mobile-gateway
本地目录：E:\API聚合

项目目标：
在 Android 手机上运行一个个人移动聚合网关，将多个本地端口、第三方 API 和 AI 模型服务聚合到统一端口和统一管理 API。

当前网络模式：
- 电脑连接 Wi-Fi 并开启移动热点
- Android 手机连接电脑热点
- 手机网关监听 0.0.0.0:8080
- 电脑浏览器通过 http://手机IP:8080/admin 访问管理界面
- 手机不消耗移动数据，纯局域网运行

用途：创建路由。

PUT /api/routes/{id}
用途：修改路由。

用途：删除路由。

PATCH /api/routes/{id}/enabled
请求：

用途：启用或禁用路由。

用途：测试路由，返回请求、响应、耗时、Token 和协议转换结果。

POST /api/routes/{id}/pull-models

十、Android Permission denied 修复记录
--------------------------------------

问题表现：
手机启动网关时报：
Cannot run program .../files/gateway/聚合网关-arm64: error=13, Permission denied

初始方案：
- 从 assets 复制中文文件名二进制到 files/gateway/
- 调用 setExecutable / chmod

最终采用方案：伪装原生库（jniLibs）。

具体修改：
1. app/build.gradle.kts 增加：
   sourceSets["main"].jniLibs.srcDirs("src/main/jniLibs")

2. GitHub Actions 构建 APK 时：
   - 下载 Go Android ARM64 二进制
   - 复制到 app/src/main/jniLibs/arm64-v8a/libgateway.so
   - 设置 chmod 755

3. Android 启动时不再从 assets 复制二进制，也不再使用中文路径。

4. GatewayProcessManager 使用：
   val nativeDir = context.applicationInfo.nativeLibraryDir
   val execFile = File(nativeDir, "libgateway.so")

5. ProcessBuilder 使用 execFile.absolutePath 启动，并将 filesDir 作为工作目录。

修复提交：
97229fa Package Android gateway as executable native library

这样 Android 系统负责将原生库解包到 nativeLibraryDir，避免普通 assets/files 目录执行权限受限。

十三、Permission denied 根因分析与方案决策（重要）
--------------------------------------------------

仓库：https://github.com/shiqi3286-create/mobile-gateway
本地目录：E:\API聚合

1. 当前问题现状
   - 伪装 libgateway.so（提交 97229fa）方案在手机上仍报 Permission denied。
   - 判断：仅把二进制放进 jniLibs 并不能保证可执行，Android 10+ 限制的是从
     应用可写私有目录直接执行程序，而非仅仅二进制本体。

2. 根因分析
   - Android 10（API 29）起，对 targetSdk >= 29 的应用执行加限：不允许执行
     应用私有可写目录（如 filesDir/runtime/）中的可执行文件。
   - 因此若把 Termux 快照解压到 filesDir/runtime/ 再执行 runtime/bin/bash，
     大概率会再次遇到与 gateway 相同的 Permission denied。
   - bash、gateway-arm64 是否被允许执行，取决于“目标目录的 SELinux 标签与
     应用 domain 的执行权限”，而不取决于是否包了 Termux。

3. 三个待确认方案
   - 方案 A（推荐，改动小）：targetSdk 35 + nativeLibraryDir 执行
     * 可执行文件放入 jniLibs/arm64-v8a/
     * 明确 android:extractNativeLibs="true"（或 Gradle useLegacyPackaging=true）
     * 从 applicationInfo.nativeLibraryDir 取 libgateway.so 执行
     * 运行时数据/配置/HTML 仍在 filesDir
   - 方案 B（兼容 Termux 快照）：targetSdk <= 28 + filesDir/runtime/bin/bash 执行
     * 接近 Termux 自身执行模型
     * 代价：新版 Android 兼容性、前台服务行为、部分商店政策
   - 方案 C（不建议）：targetSdk 35 + filesDir/runtime/bin/bash 执行
     * 极可能继续 Permission denied，不解决根本问题

   决策优先级：先评估方案 A；确认不可行后再考虑降 targetSdk 或其它受支持机制。

4. 风险点清单
   a) extractNativeLibs 风险：build.gradle.kts 已配置 jniLibs.srcDirs，但 manifest
      未设 android:extractNativeLibs="true"，也未设 useLegacyPackaging=true，
      可能未真正解包到 nativeLibraryDir，或解包后权限/路径不符预期。
   b) targetSdk 35 相关限制：私有目录执行、前台服务类型、Android 14/15 前台服务
      启动限制、WebView 明文 HTTP 策略、通知权限。若降 targetSdk 28 需单独评估。
   c) 快照制作工具链未定：本机无 Go / Java / xz，tar.exe 存在，Node 存在。
      tar.xz 很可能只能在 GitHub Actions 制作，或复用已有 Termux/Android 构建环境。
   d) Actions artifact 权限风险：确认上传/下载后 ELF 架构正确、执行权限保留、
      tar.xz 内权限位保留、解压工具不强制改写权限。
   e) Go 产物平台需确认：当前用 CGO_ENABLED=0 GOOS=android GOARCH=arm64，需验证
      产物在目标手机架构上可直接运行（ELF 64-bit / AArch64 / 正确 ABI）。
   f) WebView 仅加载静态原型：assets 中放的是web\mobile-preview/gateway-prototype.html，
      是静态前端，未接真实 fetch/SSE；后端正常也不代表页面真实刷新接口。
   g) watchdog 重启竞态：用户启动、服务自动重启、watchdog 重启、用户停止、
      onDestroy 清理需统一状态机与锁，否则可能同时起多个进程 → bind 8080 冲突。
